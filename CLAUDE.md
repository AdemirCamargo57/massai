# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Sapucaia is an offline-first Progressive Web App (PWA) for managing cattle (gado) inventory across farms (fazendas) and pastures (pastos). It is a pure front-end app — no build step, no package manager, no framework. Plain HTML/CSS/ES6 with the Firebase SDK loaded via CDN. UI text is in Brazilian Portuguese (`pt-BR`).

The repo was migrated from an earlier project called "Fazenda57" (the README still uses the old name in places, but the live app, manifest, and Firebase project are all "Sapucaia").

## Running & Developing

There is no build, lint, or test tooling. The app must be served over `http://localhost` or `https://` because Service Workers and PWA install require a secure context — opening `index.html` via `file://` will not work.

```bash
npx http-server .        # serves at http://localhost:8080
```

Default admin login password is `admin` (change it via the in-app menu after first login).

### Deploying updates / busting the cache

The Service Worker (`sw.js`) aggressively caches all assets for offline field use, so deployed changes often won't appear until the cache is invalidated. When you change `app.js`, `styles.css`, `index.html`, etc., you must also:

1. Bump `CACHE_NAME` in [sw.js](sw.js) (e.g. `sapucaia-cache-v1` → `sapucaia-cache-v2`). The `activate` handler deletes any cache whose name doesn't match the current `CACHE_NAME`.
2. Bump the visible `v14` version badge in [index.html](index.html) (appears in both the admin and parceiro headers) so the deployed version is identifiable on-device.

Users can also force a refresh in-app via the "🔄 Atualizar" menu item, which calls `app.forceAppUpdate()` — this unregisters all service workers, deletes all caches, and reloads.

## Architecture

### Single global `app` object

All application logic lives in one object literal, `app`, in [app.js](app.js) (~1500 lines). There are no modules or imports. Event handlers are wired two ways:

- Inline `onclick="app.someMethod(...)"` attributes in both [index.html](index.html) and in HTML strings generated by JS render methods. **Methods called from inline handlers must stay on the global `app` object.**
- `addEventListener` bindings set up in `app.bindEvents()` for forms and selects.

The header dropdown menu helpers (`toggleHeaderMenu`, `closeHeaderMenu`) are plain global functions defined in an inline `<script>` in `index.html`, separate from `app`.

DOM nodes are cached once in `app.cacheDOM()` and referenced as `this.xxx` thereafter.

### View switching

The app is a single page with five top-level `<div>` "views" (`login`, `admin`, `parceiro`, `report`, `history`), all hidden/shown via the `hidden` CSS class. `app.showView(name)` hides all and reveals one. There is no router/URL state. `app.routeUser()` decides which dashboard to show based on `currentUser.role`.

### Two roles

- **admin** — global view of all farms, manages farms/pastures, manages parceiro accounts and their farm access, and handles backups.
- **parceiro** (field partner) — sees only farms in their `linkedFarms` list, selects a farm+pasture, and updates cattle counts / notes / photos.

"Auth" is password-only: `handleLogin` matches the typed password against any user's `password` field in `data.users`. The logged-in user id is kept in `sessionStorage` (`loggedUserId`). Passwords are stored in plaintext in Firestore — this is a deliberately simple, low-security model for field use.

### Data model & Firestore sync

The entire application state is a single Firestore document: collection `fazenda`, document `state`. Its shape mirrors `INITIAL_DATA` in [app.js](app.js):

- `users[]` — `{ id, name, password, role, linkedFarms? }`
- `farms[]` — `{ id, name }`
- `pastures[]` — `{ id, farmId, name }`
- `cattleInventory{}` — flat map keyed by `` `${pastureId}_${categoryId}` `` → count
- `pastureDetails{}` — keyed by `pastureId` → `{ notes, photos[] }`
- `movements[]` — append-only audit log of every count change

IDs are generated with `Date.now()`. Cattle are bucketed into 10 fixed `CATEGORIES` (5 age ranges × 2 sexes); changing the categories requires editing the `CATEGORIES` constant.

`app.init()` subscribes to the `state` doc with `onSnapshot`, so the UI is reactive to remote changes. Offline persistence is enabled via `db.enablePersistence()`, and `localStorage` (key `gadoData`) is used as a secondary fallback. **Be careful with the first-load logic**: when the doc doesn't exist, the code distinguishes a server-confirmed empty (initialize with `INITIAL_DATA` and save) from an unconfirmed/cached-empty state (load from `localStorage`, do NOT save) precisely to avoid overwriting real server data on reconnect.

### Two save paths — pick the right one

- `app.saveData()` — writes the **entire** `state` document with `.set()`. Used for structural changes (adding farms, editing parceiros, importing backups). Last-write-wins; can clobber concurrent edits.
- `app.saveCattleUpdate(key, value, movement)` — writes only the single changed inventory key with `.update()` and `arrayUnion`s the movement. **This is used for cattle count changes specifically so two field workers updating different pastures simultaneously don't overwrite each other.** Prefer this pattern for any high-concurrency field write.

### Photos — Storage with Firestore fallback

`handlePhotoUpload` compresses images client-side to ≤640px JPEG (quality 0.6) via canvas before upload. Primary path uploads to Firebase Storage under `pasture-photos/{pastureId}/`. If Storage upload fails (e.g. poor connectivity — note `setMaxUploadRetryTime(10000)` forces a fast fallback), it falls back to storing the image as a base64 data URL in a `pasturePhotos` Firestore document. Max 3 photos per pasture. `getPhotoUrl(photo)` normalizes the three possible photo shapes (plain string, `{url}`, or `{firestorePhotoId}` resolved via the `photoDocCache` snapshot listener).

### Backups

Three Firestore collections beyond `state`: `pasturePhotos` (fallback photo docs), and `backups` (full-state snapshots from the admin "Backup na Nuvem" feature). Admins can also export/import the full state as a JSON file locally.

## Firebase configuration

The `firebaseConfig` is hardcoded at the top of [app.js](app.js). To repoint at a different Firebase project (e.g. for a new client/instance), replace that object and update the required Firestore + Storage security rules — the README documents the exact rules and the full "transfer to a new farm" procedure.
